# 玄鉴 v3.3.0 版本迭代计划 —— 第三部分：复测结果校验与审核机制

> 生成时间：2026-07-15 ｜ 基线：v3.1.0（tag `v3.1.0`）
> 主题：可信赖审计 —— 三层校验体系 × 证据链归档 × 质量评分
> **核心目标**：从根本上消除漏洞误报（FP）、结果伪造（Forge）、AI 幻觉（Hallucination）三类失真风险
>
> **安全红线继承**：S1（零外网流量）、S2（不修改用户代码）、S4（无危险PoC）、S7（输出目录白名单）

## 〇、版本定位与设计原则

### 0.1 问题域分析

v3.1.0 在实际红队测评中暴露的校验短板：

| 缺陷类型 | v3.1.0 表现 | 危害等级 |
|---------|------------|---------|
| 静态规则 FP | Semgrep 规则过度泛化导致"死代码中的 sink 被报为漏洞" | P1 |
| AI 幻觉 | LLM 在修复代码中生成不存在的方法名/错误的 CVE 引用 | P0 |
| 验证降级滥用 | Docker 不可用时所有 `verified_local` 被静默替换为 `simulated`，但报告未显式区分 | P1 |
| 伪造PoC | Agent 生成的 PoC 包含不可达的 payload（目标路径/参数虚构） | P0 |
| 一致性缺失 | 同一漏洞不同会话复测结果不一致（无缓存、无种子锁定） | P1 |

### 0.2 设计原则

1. **纵深防御**：三层校验独立部署，任何单层绕过不导致全链路失效
2. **可证伪性**：每个判断都关联可重现的证据链
3. **阈值透明**：所有判定阈值显式配置，拒绝硬编码魔法值
4. **零信任引擎**：对扫描器、AI Agent、LLM 输出等同施加校验
5. **最小人工依赖**：系统自测置信度 > 阈值时自动归档，仅边界案例转人工

## 二、第一层：交叉验证层

### 2.1 功能定位

对同一条 Finding 使用 ≥3 种独立方法进行验证，通过多数表决机制降低单点故障。

### 2.2 引擎池定义

| 引擎 ID | 方法名称 | 实现路径 | 适用场景 | 输出状态 |
|---------|---------|---------|---------|---------|
| `E1` | 静态规则扫描 | `fp_sentinel/scanners/semgrep_runner.py` | 代码级 sink 检测 | hit / miss |
| `E2` | AI 推理验证 | `fp_sentinel/attack/v3_ai_pentest/auto_verifier.py` | 攻击链可达性推理 | reachable / unreachable / uncertain |
| `E3` | 特征签名匹配 | `fp_sentinel/attack/target_validator.py` | 源码特征模式匹配 | match / no_match |
| `E4` | 动态无害探针 | `fp_sentinel/attack/harmless_verifier/verifier.py` | Docker 环境无害 payload | verified / simulated / failed |
| `E5` | 知识图谱关联 | `fp_sentinel/knowledge_graph/store.py` | 历史漏洞库 + 规则关联 | related / isolated |
| `E6` | LLM 自洽校验 | `fp_sentinel/validation/llm_selfcheck.py` | 生成内容的内部一致性 | consistent / inconsistent |

### 2.3 校验逻辑流程

```
输入: Finding(finding_id, rule_id, file_path, line, vuln_type, evidence)

Step 1: 引擎可用性探测
  ├─ E1: 检测 semgrep CLI 是否在 PATH
  ├─ E2: 检测 AI 模型是否在上下文窗口内可推理
  ├─ E3: 始终可用（纯字符串匹配）
  ├─ E4: shutil.which("docker") + 靶场镜像可达性
  ├─ E5: SQLite 知识图谱文件存在性
  └─ E6: LLM API 可达性 + 上下文 token 预算

Step 2: 并行执行（至少 3 个可用引擎）
  ├─ 若可用引擎数 < 2 → 降级为"人工强制审核"（不进入自动流程）
  ├─ 若可用引擎数 = 2 → 需 2/2 一致才通过
  └─ 若可用引擎数 ≥ 3 → 多数表决（≥ 2/3）

Step 3: 结果聚合
  ├─ 一致通过 → 标记 cross_validated=True，进入第二层
  ├─ 分歧 → 标记 cross_validated=False + divergence_detail
  └─ 完全对立（如 E1=hit, E2=unreachable, E3=no_match）→ 标记待人工审核
```

### 2.4 具体校验规则

#### 规则 C1：多数表决规则

```python
def _aggregate_cross_validation(engine_results: List[EngineResult]) -> CrossValidationResult:
    """多数表决 + 分歧度计算"""
    total = len(engine_results)
    positive = sum(1 for r in engine_results if r.verdict == Verdict.POSITIVE)
    negative = sum(1 for r in engine_results if r.verdict == Verdict.NEGATIVE)
    uncertain = total - positive - negative
    
    ratio = positive / total if total > 0 else 0.0
    
    # 分歧度 = 1 - |正面 - 负面| / 总数 （数值越大越分歧）
    divergence = 1.0 - abs(positive - negative) / total if total > 0 else 1.0
    
    if total < config.validation.cross_validation.degrade_threshold:
        return CrossValidationResult(
            verdict=Verdict.MANUAL_REQUIRED,
            confidence=0.0,
            reason="可用引擎数不足，降级为人工审核"
        )
    
    if ratio >= config.validation.cross_validation.min_agreement_ratio:
        return CrossValidationResult(
            verdict=Verdict.POSITIVE,
            confidence=ratio * (1 - divergence * 0.3),  # 分歧度高时降低置信度
            positive_count=positive,
            total_count=total
        )
    elif negative / total >= config.validation.cross_validation.min_agreement_ratio:
        return CrossValidationResult(
            verdict=Verdict.NEGATIVE,
            confidence=negative / total,
            positive_count=positive,
            total_count=total
        )
    else:
        return CrossValidationResult(
            verdict=Verdict.MANUAL_REQUIRED,
            confidence=1.0 - divergence,
            reason="引擎间分歧超阈值",
            divergence=round(divergence, 3)
        )
```

#### 规则 C2：引擎权重动态调整

| 场景 | 权重调整策略 |
|------|------------|
| 已知引擎历史 FP 率 > 15% | 该引擎权重 × 0.5 |
| 某引擎连续 3 次与最终结果一致 | 该引擎权重 × 1.2（上限 2.0） |
| 引擎超时未返回 | 该引擎结果不计入总权重，记录超时次数 |
| 引擎返回 `manual_required` | 该结果视为不参与投票 |

#### 规则 C3：引擎独立性验证

在上电重启或引擎池变更时，运行依赖性检测：

- 若两个引擎结果完全一致率 > 95% 且非同源 → 告警（可能存在隐式依赖）
- 若引擎 B 的代码静态引用引擎 A 的内部函数 → 标记为"非独立"，在权重计算时降级

### 2.5 失败处理流程

```
失败类型                │  自动处理流程
───────────────────────┼──────────────────────────────────────────────
引擎超时 (>120s)         │  记录为 TIMEOUT，不计入投票，告警日志
引擎池全灭 (<2 可用)      │  直接升级为「强制人工审核」，不输出自动结论
完全对立 (1:1:1)         │  标记为「意见冲突」，转人工仲裁 + 主管审批
权重衰减后仍通过          │  添加「低置信度」标签，第二层加强校验
引擎版本不匹配            │  拒绝执行，要求 `fp-sentinel validate --sync-engines`
```

## 三、第二层：内容真实性校验层

### 3.1 功能定位

确保 Finding 内容中引用的证据、PoC 路径、可达性判断与实际代码/环境状态一致，**重点防范 AI 幻觉和伪造攻击路径**。

### 3.2 校验维度分解

#### 3.2.1 维度 A：AST 一致性校验

校验 AI 生成的修复代码（Auto PR）是否与上下文语法环境兼容。

| 校验项 | 方法 | 阈值 |
|-------|------|------|
| 方法存在性 | 在项目全局 search call 引用，确认变量/方法已定义 | 未定义引用数 = 0 |
| import 完备性 | 解析生成代码的 import 链，确认依赖已在项目依赖清单 | 未解析 import 数 = 0 |
| 类型签名匹配 | 函数参数/返回值是否与上下文类型注解一致 | 类型错误数 = 0 |
| 可达性确认 | 修复代码中的新路径是否在控制流图中可达 | 无可报错 = 0 |

**校验流程**：

```python
def validate_ast_consistency(patch: FixPatch, project_context: ProjectContext) -> ASTCheckResult:
    """
    1. 对 patch 中的 "+" 行做增量 AST 解析
    2. 提取所有 Name/Attribute 引用
    3. 在 project_context 中查找每个引用的定义
    4. AST 解析失败 → 立即标记「语法错误」
    5. 未解析引用 > 0 → 标记「AST 不一致」
    """
    errors = []
    undefined_refs = []
    
    try:
        tree = ast.parse(patch.new_code)
    except SyntaxError as e:
        return ASTCheckResult(
            passed=False,
            error_type="syntax_error",
            detail=f"语法错误 @ L{e.lineno}: {e.msg}"
        )
    
    # 提取所有引用节点
    for node in ast.walk(tree):
        if isinstance(node, ast.Name):
            ref = node.id
            if not project_context.is_defined(ref, patch.file_path, patch.line_start):
                undefined_refs.append(ref)
        elif isinstance(node, ast.Attribute):
            ref = ast.dump(node)
            if not project_context.is_attribute_defined(ref, patch.file_path):
                undefined_refs.append(ref)
    
    # 阈值校验
    if len(undefined_refs) > config.validation.authenticity.forgery_detection.max_undefined_refs:
        return ASTCheck-result(
            passed=False,
            error_type="undefined_reference",
            undefined_refs=undefined_refs,
            detail=f"发现 {len(undefined_refs)} 个未定义引用，疑似 AI 幻觉"
        )
    
    return ASTCheckResult(passed=True)
```

#### 3.2.2 维度 B：反伪造 PoC 校验

校验 PoC 中引用的路径、参数与实际靶场/代码的一致性。

| 伪造类型 | 检测规则 | 自动处置 |
|---------|---------|---------|
| 路径虚构 | PoC 中的 URL 路径在路由表中不匹配 | 直接标记 FP + 不可归档 |
| 参数注入 | PoC payload 使用未定义的参数名 `?{param}=...` | 标记"参数幻觉"转人工 |
| 依赖链伪造 | 攻击链经过的中间节点在该版本代码中不存在 | 标记"链不可达"删除该链 |
| 环境假设 | PoC 依赖 `phpinfo()` / `debug=true` 等调试信息 | 补充"前提条件不可达"说明 |
| 时间戳伪造 | 验证时间戳 > 当前服务器时间或 < 首次发现时间 | 标记"数据伪造嫌疑" |

**路由可达性验证流程**：

```python
def validate_poc_reachability(poc: PoC, target_routes: List[Route]) -> ReachabilityResult:
    """
    1. 解析 PoC 请求路径 pattern
    2. 在 target_routes 中查找匹配（含通配符、REST 参数替换）
    3. 若路径不存在 → 检查是否为已知历史路由（版本可能已变更）
    4. 路径存在 → 提取查询参数名
    5. 在路由处理函数 AST 中查找参数使用
    6. 如有参数不存在于处理函数 → 标记"虚构参数"
    """
    route_match = _match_route(poc.path, target_routes)
    
    if not route_match:
        # 辅助判定：是否为该路由的旧版本别名
        if _is_legacy_alias(poc.path, target_routes):
            return ReachabilityResult(
                reachable=False,
                reason="路由已更新，路径已失效",
                deprecation_info=_get_current_equivalent(poc.path)
            )
        return ReachabilityResult(
            reachable=False,
            reason="目标路径不可达",
            forgery_type="path_hallucination"
        )
    
    # 参数校验
    undefined_params = []
    for param in poc.query_params:
        if not _param_used_in_handler(param, route_match.handler_ast):
            undefined_params.append(param)
    
    if undefined_params:
        return ReachabilityResult(
            reachable=True,  # 路径可达但参数虚构
            forgery_type="param_hallucination",
            undefined_params=undefined_params,
            partial_reachability=True
        )
    
    return ReachabilityResult(reachable=True)
```

#### 3.2.3 维度 C：时效性校验

确保 Findings 不会引用过期或已被修复的代码版本。

| 校验项 | 机制 | 过期处理 |
|-------|------|---------|
| Git 提交一致性 | 对比 Finding 中的 `last_commit_sha` 与当前 HEAD | 不一致时重新扫描验证 |
| 代码行号漂移 | Finding 行号 ±5 行的内容哈希 vs 当前文件对应位置哈希 | 漂移超阈值 → 标记"位置偏移"重新定位 |
| 修复状态回查 | 在 Git 历史中查找对 Finding 路径的后续 commit | 若发现修复 → 自动关闭 Finding |
| 依赖版本一致性 | Finding 关联的漏洞 CVE 是否在当前依赖版本中已修补 | 已修补 → 降级为"理论风险" |

### 3.3 真实性评分算法

```python
def compute_authenticity_score(finding: Finding, context: ValidationContext) -> float:
    """
    真实性评分 = Σ(维度得分 × 权重) / Σ权重
    权重配置：
      - AST 一致性: 0.30
      - PoC 可达性: 0.35
      - 时效性: 0.20
      - 历史一致性: 0.15
    """
    w_ast, w_poc, w_time, w_hist = 0.30, 0.35, 0.20, 0.15
    
    # AST 一致性得分
    ast_result = validate_ast_consistency(finding.patch, context.project)
    s_ast = 1.0 if ast_result.passed else max(0.0, 1.0 - len(ast_result.undefined_refs) * 0.2)
    
    # PoC 可达性得分
    poc_result = validate_poc_reachability(finding.poc, context.target_routes)
    s_poc = 1.0 if poc_result.reachable and not poc_result.forgery_type else (
        0.5 if poc_result.partial_reachability else 0.0
    )
    
    # 时效性得分
    time_result = validate_freshness(finding, context.current_git_head)
    s_time = 1.0 if time_result.fresh else max(0.0, 1.0 - time_result.staleness_hours / 168)
    
    # 历史一致性得分（复测是否与上次一致）
    hist_result = validate_historical_consistency(finding, context.history)
    s_hist = 1.0 if hist_result.consistent else 0.3
    
    score = w_ast * s_ast + w_poc * s_poc + w_time * s_time + w_hist * s_hist
    return round(min(1.0, max(0.0, score)), 4)
```

### 3.4 失败处理流程

```
低分项              │  阈值  │  自动处置
────────────────────┼────────┼─────────────────────────────────────
AST 一致性 < 0.7    │  0.7   │  拒绝归档 + 标"AI幻觉" + 触发引擎 E6 自检
PoC 不可达           │  0.0   │  直接标 FP + 拒绝归档
时效性 < 0.5        │  0.5   │  标记"已过期" + 强制触发复测
部分伪造            │  0.5   │  标记"部分可信" + 仅归档有效片段
评分 ≥ 0.75         │  0.75  │  通过进入第三层
评分 < 0.75         │  0.75  │  拒绝自动归档 + 转人工审核队列
完全伪造 (评分=0)    │  0.0   │  记录为"伪造案例" + 反馈训练集标记
```

## 四、第三层：人工抽检层

### 4.1 功能定位

引擎无法拍板的边界案例 + 随机质量抽检 + 质量评分闭环。

### 4.2 分层抽样策略

采用**风险加权 + 置信度加权**的复合抽样算法：

```python
def compute_sample_probability(finding: Finding, quality_score: float) -> float:
    """
    基础抽样概率:
      - CRITICAL (CVSS ≥ 9.0) = 100% 必须审核
      - HIGH (CVSS 7.0-8.9)    = 20%
      - MEDIUM (CVSS 4.0-6.9)  = 10%
      - LOW (CVSS < 4.0)       = 5%
    
    置信度修正:
      - quality_score ≥ 0.95 → 概率 × 0.5 (低分险自动豁免)
      - quality_score < 0.60 → 概率 × 2.0 (低置信度必须人工确认)
      - 历史 FP 率 > 20% 的同规则 Finding → 概率 × 1.5
    
    最终概率 clamp 到 [0.01, 1.0]
    """
    base = config.validation.spot_check.stratified_sample.get(
        finding.severity.value, 0.05
    )
    
    confidence_factor = 1.0
    if quality_score >= 0.95:
        confidence_factor = 0.5
    elif quality_score < 0.60:
        confidence_factor = 2.0
    
    fp_rate_factor = 1.0
    rule_fp_rate = get_rule_historical_fp_rate(finding.rule_id)
    if rule_fp_rate > 0.20:
        fp_rate_factor = 1.0 + (rule_fp_rate - 0.20) * 2.5
    
    final_prob = min(1.0, base * confidence_factor * fp_rate_factor)
    return max(0.01, final_prob)
```

### 4.3 仲裁机制

当多个引擎结果对立时，进入仲裁模式：

```
仲裁模式触发条件:
  ├─ 引擎投票结果 = 2:1（接近阈值但未达 2/3）
  ├─ 关键漏洞（CRITICAL）任一引擎报 negative
  └─ 质量评分在 [0.60, 0.75) 的灰色地带

仲裁流程:
  Step 1: 由主审引擎（优先级最高者）提交详细推理报告
  Step 2: 副审第二名引擎做独立申诉
  Step 3: 若两引擎仍对立 → 人工仲裁员介入
  Step 4: 仲裁员的判定作为 ground truth 入库
  Step 5: 每周汇总仲裁数据，动态调整引擎权重
```

#### 5.1.2 证据链结构

```python
@dataclass
class EvidenceItem:
    item_id: str                          # UUID v7
    finding_id: str                       # 关联 Finding
    evidence_type: EvidenceType           # CODE_SNAPSHOT / LOG_OUTPUT / SCREENSHOT / POC_PROOF / HUMAN_JUDGMENT
    content: str                          # 内容（文本或 base64）
    content_hash: str                     # SHA-256(content)
    timestamp: str                        # ISO 8601
    source_engine: str                    # 哪个引擎/审核员产生
    confidence: float = 1.0               # 该证据自身的可信度


@dataclass
class EvidenceChain:
    chain_id: str = ""                    # UUID v7
    finding_id: str = ""
    items: List[EvidenceItem] = field(default_factory=list)
    chain_hash: str = ""                  # Merkle tree root hash
    created_at: str = ""
    sealed: bool = False                  # 封签后不可修改
    
    def add_item(self, item: EvidenceItem):
        if self.sealed:
            raise EvidenceChainSealedError("证据链已封签，拒绝追加")
        self.items.append(item)
        self._recompute_hash()
    
    def seal(self):
        self.sealed = True
        self.chain_hash = self._compute_merkle_root()
```

#### 5.1.3 归档规则

| 触发条件 | 归档内容 | 保留策略 |
|---------|---------|---------|
| Finding 通过三层校验 | 全部证据链 + 校验日志 | 永久保留 |
| 人工审核通过 | 以上 + 审核员判定理由 | 永久保留 |
| 人工审核拒绝 | 以上 + 误报原因标注 | 永久（训练用） |
| 引擎超时失败 | 请求/响应日志 + 堆栈跟踪 | 90 天后归档 |
| 数据伪造事件 | 全部中间状态快照 | 永久（审计用） |

#### 5.1.4 完整性校验

每次证据链写入时：
1. 计算每个 EvidenceItem 的 `SHA-256(content)` 写入 `content_hash`
2. 将所有 item hash 构造 Merkle Tree，根哈希作为 `chain_hash`
3. 写入 SQLite 时追加 HMAC-SHA256(secret_key, chain_hash) 作为签名
4. 查询时重新计算 chain_hash 与存储值比对

### 5.2 质量评分体系

#### 5.2.1 评分模型

```python
@dataclass
class QualityScore:
    """Finding 最终质量评分"""
    finding_id: str
    score: float                    # 0.0 - 1.0
    confidence_interval: Tuple[float, float]  # 95% 置信区间
    
    # 子维度得分
    cross_validation_score: float   # 交叉验证一致率
    authenticity_score: float       # 真实性评分
    human_review_score: float       # 人工审核得分（若有）
    temporal_consistency_score: float  # 跨时段一致性
    
    # 评分等级
    grade: QualityGrade             # S / A / B / C / D
    
    computed_at: str
    expires_at: str                 # 评分有效期（代码变更后失效）


class QualityGrade(str, Enum):
    S = "S"   # score >= 0.95 — 极高置信度，可自动化处置
    A = "A"   # score >= 0.85 — 高置信度，推荐自动化
    B = "B"   # score >= 0.70 — 中等置信度，建议自动化+标志
    C = "C"   # score >= 0.55 — 低置信度，需人工复核
    D = "D"   # score < 0.55 — 极低置信度，仅存档不报告
```

#### 5.2.2 评分计算公式

```python
def compute_final_quality_score(
    finding: Finding,
    cv_result: CrossValidationResult,
    auth_score: float,
    human_result: Optional[HumanReviewResult],
    temporal_score: float
) -> QualityScore:
    """
    最终评分 = 加权合成:
    - 交叉验证得分: 权重 0.25
    - 真实性得分:   权重 0.30
    - 人工审核得分: 权重 0.30（无人工审核时使用交叉验证×真实性默认值）
    - 时效一致性:   权重 0.15
    """
    w_cv, w_auth, w_human, w_time = 0.25, 0.30, 0.30, 0.15
    
    cv_score = cv_result.confidence if cv_result.verdict != Verdict.NEGATIVE else 0.0
    human_score = human_result.score if human_result else (cv_score * auth_score)
    
    raw_score = (
        w_cv * cv_score +
        w_auth * auth_score +
        w_human * human_score +
        w_time * temporal_score
    )
    
    # 置信区间计算（Wilson score interval 近似）
    ci_low, ci_low = _compute_confidence_interval(raw_score, sample_size=cv_result.total_count)
    
    grade = _score_to_grade(raw_score)
    expires_at = (datetime.now(timezone.utc) + timedelta(hours=168)).isoformat()  # 7天有效
    
    return QualityScore(
        finding_id=finding.finding_id,
        score=round(raw_score, 4),
        confidence_interval=(round(ci_low, 4), round(ci_high, 4)),
        cross_validation_score=round(cv_score, 4),
        authenticity_score=round(auth_score, 4),
        human_review_score=round(human_score, 4),
        temporal_consistency_score=round(temporal_score, 4),
        grade=grade,
        computed_at=datetime.now(timezone.utc).isoformat(),
        expires_at=expires_at
    )
```

#### 5.2.3 评分衰减与刷新

| 场景 | 衰减策略 |
|------|---------|
| Finding 超过 7 天未复测 | 评分 × 0.95 / 天 |
| 代码发生变更（commit diff 触及 Finding 文件） | 立即失效，强制重新评分 |
| 关联漏洞 CVE 状态变更 | 降一级（S→A, A→B...） |
| 发现该规则误报率上升 | 该规则全部 Finding 评分 × 0.9 |
| 人工审核结果与自动评分不符 | 以人工考核分覆盖，触发规则调优 |
