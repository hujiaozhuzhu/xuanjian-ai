## 一、版本定位与目标

### 1.1 版本代号

**Argus** — 取自古希腊百眼巨人"阿耳戈斯"，寓意 v3.3 版本将建立对安全验证全场景的覆盖与监控能力，实现"永不遗漏"的复测保障。

### 1.2 核心定位

v3.3 是玄鉴从"安全审计平台"升级为"安全能力基础设施"的关键奠基版本。v3.0~v3.2 已完成漏洞发现、自动修复、AI 渗透测试、行业基准对比等核心能力建设，但在以下维度存在系统性短板：

| 维度 | 现有状态 | v3.3 目标 |
|------|----------|-----------|
| 复测覆盖 | 仅支持源代码层的 SAST 复测 | 支持 Web/中间件/数据库/OS 四层全场景复测 |
| 流程规范 | 验证流程散落在各模块，无统一编排 | 建立统一的复测流程规范，可配置、可审计 |
| 验收标准 | 缺少量化验收门槛（覆盖率、效率） | 建立分层验收标准，指标可度量、可考核 |
| 回归保障 | 手动触发为主，缺少自动化回归管道 | 接入 CI/CD 事件驱动自动回归，阻断风险上线 |

### 1.3 设计原则

1. **向后兼容**：新增能力不影响现有 SAST/PR/AI 渗透功能，所有复测能力以插件形式扩展。
2. **分层解耦**：Web/中间件/数据库/OS 四层复测引擎独立实现，通过统一编排层调度。
3. **安全第一**：复测操作仅限于非破坏性验证（读操作、无害 Payload、靶场环境），继承 S1/S4 红线约束。
4. **可观测性**：每次复测输出结构化报告，记录覆盖率、耗时、发现项等指标，支持趋势分析。

### 1.4 目标用户

| 用户群体 | 使用场景 | 核心价值 |
|----------|----------|----------|
| 安全工程师 | 修复确认、回归验证 | 一键验证修复有效性，无需手动构造测试 |
| DevOps 工程师 | CI/CD 质量门禁 | 上线前自动复测，阻断已知漏洞流入生产 |
| 安全负责人 | 度量 & 复测报告 | 量化安全验收指标，支持合规审计 |
| 红队 & 渗透测试 | 攻击链复测 | 验证攻击链利用路径是否被有效阻断 |

### 2.2 Web 层复测引擎

**模块路径**：`fp_sentinel/retest/engines/web_engine.py`

**功能定位**：对 HTTP/HTTPS 接口进行漏洞修复有效性的自动化复测，覆盖 OWASP Top 10 高危场景。

#### 2.2.1 技术实现思路

```python
class WebRetestEngine:
    """
    Web 层复测引擎
    
    输入：漏洞报告（含 PoC、修复后目标地址）
    输出：复测结论（已修复 / 未修复 / 需人工确认）
    """

    def __init__(self, config: WebRetestConfig):
        self.browser_engine = BrowserEngine()  # 复用 fp_sentinel/browser/
        self.payload_variants = PayloadVariants()  # 复用 attack/payload_variants.py
        self.harmless_verifier = HarmlessVerifier()  # 复用 attack/harmless_verifier/
        self.session_manager = SessionManager()  # 复用 auth/session.py

    async def verify(self, finding: Finding) -> RetestResult:
        """
        核心复测流程：
        1. 加载漏洞对应的 Payload 模板链
        2. 生成无害验证变体（3~5 个变种）
        3. 按顺序注入并观察响应
        4. 基于响应差异判定修复状态
        """
        payloads = self.payload_variants.generate(
            vuln_type=finding.vuln_type,
            variant_mode="verify_only"  # 仅生成验证性 Payload
        )
        results = []
        for payload in payloads:
            response = await self._safe_inject(finding.url, payload)
            results.append(self._analyze_response(response, finding.expected_fix_signature))
        return self._aggregate_verdict(results)
```

**关键子能力**：

| 子能力 | 复用/新建 | 技术说明 |
|--------|----------|----------|
| 浏览器自动化复测 | 复用 `browser/engine.py` + Playwright | 支持 SPA 渲染、AJAX 请求拦截、DOM Clobbering 检测 |
| Payload 变异注入 | 复用 `attack/payload_variants.py` | 针对已发现漏洞，生成 3~5 个无害验证变体（不含真实攻击载荷） |
| 响应签名比对 | 新建 `retest/matchers/response_matcher.py` | 基于修复后预期的响应签名（状态码/响应体特征/Header）判定修复状态 |
| 登录态保持 | 复用 `auth/session.py` | 支持 cookie/token 注入，确保复测在认证态下执行 |
| CSRF Token 处理 | 新建 `retest/helpers/csrf_handler.py` | 自动抓取和附加 CSRF Token |
| WAF 误报识别 | 新建 `retest/filters/waf_false_positive.py` | 区分 WAF 拦截与真实修复，避免误判 |

#### 2.2.2 复测 Payload 安全约束

所有 Web 层复测 Payload 必须满足以下条件：

- 仅使用验证性 Payload（如 `SELECT 1` 而非 `SELECT password FROM users`）
- 不涉及数据读取/写入/删除
- 不涉及权限提升或横向移动
- 执行前必须经过 `HarmlessVerifier` 静态分析
- 所有 Payload 操作记录写入审计日志

#### 2.2.3 输入输出

**输入**：漏洞 Finding 对象，包含 `url`、`vuln_type`、`original_poc`、`fix_commit` 字段。

**输出**：`RetestResult` 对象，包含：

```python
@dataclass
class RetestResult:
    finding_id: str
    verdict: Verdict          # PASSED / FAILED / INCONCLUSIVE
    confidence: float         # 0.0~1.0，越高越确信
    variants_tested: int      # 测试的变体数量
    variants_blocked: int     # 被修复拦截的变体数量
    response_snapshots: List[ResponseSnapshot]  # 原始响应用于审计
    tested_at: datetime
    evidence_url: str         # 详细证据链接
```

### 2.3 中间件层复测引擎

**模块路径**：`fp_sentinel/retest/engines/middleware_engine.py`

**功能定位**：对常见中间件（Nginx/Apache/Tomcat/Redis/RabbitMQ/Kafka/Nacos/Zookeeper）的配置安全、版本漏洞、弱口令进行自动化复测。

#### 2.3.1 技术实现思路

```python
class MiddlewareRetestEngine:
    """
    中间件层复测引擎
    
    通过 TCP 端口探测 + 协议握手 + 特征指纹 识别中间件类型，
    然后针对已发现漏洞执行协议级复测验证。
    """

    # 内置中间件指纹库
    SIGNATURE_DB: Dict[str, MiddlewareSignature] = {
        "redis": MiddlewareSignature(port=6379, banner_prefix="redis", probe_command="PING"),
        "nginx": MiddlewareSignature(port=80, header="Server: nginx", probe_command="GET / HTTP/1.0"),
        "rabbitmq": MiddlewareSignature(port=5672, banner_prefix="AMQP", probe_command=None),
        # ... 8 种常见中间件
    }

    async def verify(self, finding: MiddlewareFinding) -> RetestResult:
        # 1. 探测中间件存活和版本
        version = await self._detect_version(finding.target.ip, finding.target.port)
        # 2. 加载对应复测方案
        retest_plan = self._load_plan(finding.vuln_type, finding.middleware_type)
        # 3. 执行协议级验证（非侵入式）
        for check in retest_plan.checks:
            result = await self._protocol_verify(finding.target, check)
            if not result.blocked:
                return RetestResult(verdict=Verdict.FAILED, ...)
        return RetestResult(verdict=Verdict.PASSED, ...)
```

**复测矩阵**：

| 中间件 | 支持的复测场景 | 协议/方式 | 复测手段 |
|--------|---------------|----------|----------|
| Nginx / Apache | 版本漏洞、配置错误（目录列表、方法允许） | HTTP | 构造特定请求观察响应状态 |
| Tomcat | 弱口令、WAR 部署漏洞、AJP Ghostcat | HTTP + AJP | 探测 manager 接口可达性 |
| Redis | 未授权访问、弱口令、版本漏洞 | RESP | AUTH 探测 + INFO 版本校验 |
| RabbitMQ | 未授权访问、默认凭证、插件漏洞 | AMQP + HTTP | management API 探测 |
| Kafka | 未授权访问、SASL 配置 | Kafka Protocol | Metadata 请求探测 |
| Nacos | 未鉴权、默认 Token、CVE | HTTP | API 探测 + 配置接口可达性 |
| ZooKeeper | 未授权访问、版本漏洞 | ZAB | `envi` 四字命令 |
| etcd | 未授权访问、版本漏洞 | HTTP/gRPC | `/version` + `/health` 探测 |

#### 2.3.2 安全约束

- 中间件复测仅执行"读操作"（INFO、version 探测、配置读取），不执行任何写操作
- 弱口令检测仅校验"已有弱口令列表是否被修改"，不进行暴力枚举
- Redis/Tomcat 等高风险的复测必须在靶场环境执行，禁止直连生产实例

### 2.4 数据库层复测引擎

**模块路径**：`fp_sentinel/retest/engines/database_engine.py`

**功能定位**：对数据库用户权限、访问控制、加密配置、已知 CVE 进行复测验证。

#### 2.4.1 技术实现思路

```python
class DatabaseRetestEngine:
    """
    数据库层复测引擎
    
    通过数据库连接执行只读查询，验证：
    1. 漏洞相关的权限是否被回收
    2. 弱口令是否被修改
    3. 加密配置是否生效
    4. 补丁版本是否与修复报告一致
    """

    SUPPORTED_DATABASES = {"mysql", "postgresql", "mongodb", "redis", "oracle"}

    async def verify(self, finding: DatabaseFinding) -> RetestResult:
        conn = await self._safe_connect(finding.target, read_only=True)
        try:
            check = self._dispatch_check(finding.vuln_type)
            result = await check.run(conn, finding.expected_fix)
            return RetestResult(
                verdict=Verdict.PASSED if result.blocked else Verdict.FAILED,
                evidence=result.query_result
            )
        finally:
            await conn.close()
```

**复测矩阵**：

| 数据库 | 复测场景 | 复测手段 |
|--------|----------|----------|
| MySQL | 弱口令、过度授权、UDF 执行、SSL 配置 | `SELECT` 验证权限边界，`SHOW` 验证配置 |
| PostgreSQL | 弱口令、public schema 权限、扩展权限 | `\du` + 信息_schema 查询 |
| MongoDB | 未授权访问、默认端口、权限配置 | `connectionStatus` + `listDatabases` |
| Redis | 未授权访问、CONFIG 命令、版本 | `AUTH` + `INFO server` |
| Oracle | TNS 注入、弱口令、版本 | `banner` 信息获取 + 权限查询 |

> **安全约束**：数据库复测仅允许 SELECT/SHOW/DESC 等只读操作，严禁 DML/DDL。连接必须使用只读账号，禁止 SA 连接。

### 2.5 OS 层复测引擎

**模块路径**：`fp_sentinel/retest/engines/os_engine.py`

**功能定位**：对操作系统级别的安全基线（文件权限、服务配置、补丁版本、内核参数）进行复测验证。

#### 2.5.1 技术实现思路

```python
class OSRetestEngine:
    """
    操作系统层复测引擎
    
    支持两种复测模式：
    1. SSH 远程命令执行（适用于连通的内网主机，需 ssh key 认证）
    2. Agent 模式（通过已部署的玄鉴 Agent 拉取信息，适用于 Agent 已装机环境）
    """

    BASELINE_CHECKS: Dict[str, Callable] = {
        "file_permission": "_check_file_permission",
        "service_status": "_check_service_status",
        "kernel_param": "_check_kernel_parameter",
        "patch_version": "_check_patch_level",
        "user_audit": "_check_user_privilege",
        "firewall_rule": "_check_firewall_config",
    }

    async def verify(self, finding: OSFinding) -> RetestResult:
        if finding.target.has_agent:
            return await self._agent_mode_verify(finding)
        elif finding.target.ssh_reachable:
            return await self._ssh_mode_verify(finding)
        else:
            return RetestResult(
                verdict=Verdict.INCONCLUSIVE,
                reason="目标不支持 SSH 且未安装 Agent，无法执行 OS 层复测"
            )
```

**复测矩阵**：

| 检查项 | 检测方法 | 适用平台 |
|--------|----------|----------|
| 文件权限 | `stat` + `ls -l` 校验关键文件权限 | Linux / macOS |
| 目录权限 | 校验 `/etc/passwd`、`/etc/shadow`、`/tmp` 等 | Linux |
| 服务端口 | `ss -tlnp` + `netstat` 校验暴露端口 | Linux |
| 内核参数 | `sysctl` 校验关键安全参数（ASLR、npf） | Linux |
| 补丁级别 | `uname -r` + 包管理器版本核对 | Linux |
| 用户审计 | `/etc/passwd` + `sudoers` 配置审计 | Linux |
| 防火墙规则 | `iptables -L` / `firewall-cmd --list-all` | Linux |
| 账号策略 | `/etc/login.defs` + PAM 配置 | Linux |

> **安全约束**：OS 层复测严格执行"只读"策略，所有检查通过 `get` 命令实现，不支持任何修改操作。SSH 连接强制使用密钥认证，禁止密码登录。

## 三、基础复测流程规范

### 3.1 复测生命周期

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  触发     │───→│  预备     │───→│  执行     │───→│  判定     │───→│  归档     │
│ Trigger  │    │ Prepare  │    │ Execute  │    │ Judge    │    │ Archive  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     │               │               │               │               │
  事件/手动       目标发现         并行引擎        规则判定       报告生成
  定时任务       环境准备         安全注入        置信度计算      数据落库
                 Payload 生成    响应采集        趋势对比        审计追溯
```

### 3.2 触发方式

| 触发方式 | 适用场景 | 技术实现 | 优先级 |
|----------|----------|----------|--------|
| **CI/CD 事件驱动** | 代码合并/部署发布时自动触发关联漏洞的复测 | 复用 `devops/webhook_handler.py` 扩展 | P0 |
| **定时全量扫描** | 每日/每周对所有 `状态=已修复` 的 Finding 发起复测 | APScheduler / cron 调度 | P0 |
| **手动即时触发** | 安全工程师针对特定漏洞触发复测 | CLI `xuanjian retest run <finding-id>` | P1 |
| **安全工单联动** | 修复工单关闭时自动触发复测 | 与工单系统（Jira/TAPD）Webhook 联动 | P2 |
| **版本发布门禁** | 版本发布流水线中的强制复测卡点 | 在 pipeline_gate.py 中增加复测门禁 | P1 |

### 3.3 预备阶段规范

**目标发现**：

```yaml
# 复测目标发现配置示例 (retest_config.yaml)
targets:
  discovery:
    sources:
      - type: cmdb
        endpoint: "http://cmdb.internal/api/ci"
        sync_interval: "1h"
        filter: "env in [staging, prod] and app in ${monitored_apps}"
      - type: cicd_webhook
        events: [deploy_success, pr_merge]
        extract_targets: true
      - type: manual
        entries:
          - name: "payment-api"
            type: web
            url: "https://pay.staging.example.com"
            tags: [critical, payment]
```

**Payload 生成规范**：

每个漏洞类型的复测 Payload 遵循"无害验证原则"：

1. **SQL 注入**：用 `SELECT 1` `SELECT 1=1` `-- 修复验证标记` 等无数据读取的表达式
2. **XSS**：用 `<svg>` 或 `<img src=x>` 等触发错误但不执行脚本的标签
3. **命令注入**：用 `echo retest_verify_2026` 等无害回显命令
4. **路径遍历**：用 `....//....//etc/hostname` 等低风险探测路径
5. **SSRF**：仅请求已知的内网元数据接口（如 `http://169.254.169.254/latest/meta-data/hostname`）的连通性

**所有 Payload 必须经过 HarmlessVerifier 扫描**，确保不含数据窃取、横向移动、危害性操作的变体。

### 3.4 执行阶段规范

**并行调度策略**：

```python
class RetestScheduler:
    """
    复测调度器 - 控制并行度、资源隔离、超时熔断
    """

    DEFAULT_CONFIG = {
        "max_parallel_per_target": 3,      # 同一目标最多 3 并发
        "max_parallel_global": 10,         # 全局最大 10 并发
        "timeout_per_check": 30,           # 单个检查 30 秒超时
        "timeout_global": 300,             # 整个复测任务 5 分钟超时
        "retry_count": 2,                  # 失败重试 2 次
        "retry_delay": 5,                  # 重试间隔 5 秒
        "cooldown_between_targets": 2,     # 两目标之间 2 秒冷却
        "abort_on_target_unreachable": False,  # 目标不可达不中断整体流程
    }
```

**执行时序**：

```
1. 加载待复测的 Finding 列表（过滤：状态=已修复 AND 修复时间 > 24h AND 最近未复测）
2. 按引擎类型分组（Web/Middleware/DB/OS）
3. 各引擎并行执行：
   a. 连接目标（TCP/HTTP/SSH 握手）
   b. 执行验证检查序列（按检查脚本顺序）
   c. 采集响应/状态/输出
4. 超时检查：超时项标记为 INCONCLUSIVE，不阻塞整体流程
5. 结果汇总：按 Finding 聚合各引擎的验证结果
```

**熔断与容错**：

| 场景 | 应对策略 |
|------|----------|
| 目标不可达 | 标记 INCONCLUSIVE，记录错误原因，不阻塞其他复测项 |
| Payload 被 WAF 拦截 | 自动切换备用 Payload 变体，记录 WAF 拦截次数 |
| 引擎异常（超时/崩溃） | 自动重试 + 降级为上一个已知状态，触发告警 |
| 批量复测中单任务失败 | 失败任务进入重试队列，不影响整体进度 |
| 新发现高危问题 | 可选配置“实时阻断”或“仅记录不阻断”（建议仅记录，需人工确认） |

### 3.5 判定阶段规范

**判定规则引擎**：

```python
class VerdictEngine:
    """
    复测判定引擎
    
    基于多维度信号综合计算复测结论：
    - Payload 拦截率 = blocked / total
    - 置信度 = Weighted(signal1, signal2, ...)
    - 对照修复前后的响应差异
    """

    THRESHOLDS = {
        "strict": VerdictConfig(           # 严格模式：用于生产环境）
            pass_threshold=1.0,            # 所有变体必须被拦截
            min_confidence=0.95,
            require_all_engines=True       # 所有引擎都通过
        ),
        "normal": VerdictConfig(           # 常规模式（默认）
            pass_threshold=0.9,            # 90% 以上变体被拦截
            min_confidence=0.80,
            require_all_engines=False      # 主引擎通过即可
        ),
        "loose": VerdictConfig(            # 宽松模式：开发环境快速验证
            pass_threshold=0.7,
            min_confidence=0.60,
            require_all_engines=False
        ),
    }
```

**判定输出**：

| 判定结果 | 含义 | 后续动作 |
|----------|------|----------|
| **PASSED（已修复）** | 复测验证通过，修复有效 | 更新 Finding 状态为"复测通过"，记录复测时间和证据 |
| **FAILED（未修复）** | 修复无效，漏洞仍可利用 | 自动打开新工单，关联原始 Finding，触发告警通知 |
| **INCONCLUSIVE（无法判定）** | 目标不可达/WAF 干扰/Payload 全部无效 | 记录为"需人工确认"，派发安全工程师手工验证任务 |

**趋势分析**：

每次复测结果与历史复测对比，计算：
- 修复有效率 = PASSED 数 / (PASSED + FAILED) 数
- 修复衰减率 = 随时间推移，PASSED → FAILED 的转换率
- 复测覆盖率 = 已复测的已修复 Finding / 全部已修复 Finding

### 4.2 效率指标

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|

| **目标连通性探测** | ≤ 5 秒/目标 | TCP/HTTP 握手 + 服务识别 |

| **CLI 命令启动时间** | ≤ 1 秒 | 命令行响应延迟（冷启动） |
| **并发复测能力** | ≥ 10 个目标 | 不阻塞、不降级响应质量 |
| **资源占用（宿主机）** | CPU ≤ 20%，内存 ≤ 512MB | 复测引擎常驻运行时监控 |

### 4.3 稳定性指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| **复测任务成功率** | ≥ 98% | 排除目标不可达等非引擎原因的失败 |

| **长时间运行稳定性** | 7 天无内存泄漏 | 持续复测场景下内存增长 ≤ 10MB |
