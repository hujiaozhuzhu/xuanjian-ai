## 〇、设计原则与范围

### 核心理念

v3.3.0 聚焦于将 v3.1/v3.2 已建成的模块能力串联为「扫描 → 分析 → 修复 → 验证 → 运营」的完整闭环。第二部分重点覆盖三大能力域：

3. **合规与运营能力**：为团队提供等保适配、运营度量、批量复测工具

## 一、智能分析体系

### 1.1 修复效果评估模型

#### 目标

在现有漏洞发现能力基础上，构建「修复前后对比量化评估」能力。每次扫描后自动判断：
- 哪些已知漏洞已修复（fingerprint 消失）
- 是否引入新的同类型漏洞（修复不完整或误引入）
- 修复后残余风险评分

#### 数据流转逻辑

```
[最新扫描 findings]
       │
       ▼
[Fingerprint 匹配层]
  ├── 与 findings 表中上一轮 fingerprint 精确比对
  ├── 消失项 → FIXED（已修复）
  ├── 新增项 → NEW（新增漏洞）
  └── 仍存在 → PERSISTENT（未修复）
       │
       ▼
[修复质量评估层]
  ├── 对 FIXED 项：检索对应修复 commit diff → 检查是否存在"表面修复"模式
  │    （如仅加注释、仅变更变量名、仅删除 log 但未修复参数化）
  ├── 对 PERSISTENT 项：计算持续暴露天数 = 当前 - 首次发现日期
  └── 对 NEW 项：关联同文件修复 commit → 判断是否修复引入
       │
       ▼
[残余风险评分层]
  残余风险 = Σ(PERSISTENT 项 risk_score × 持续天数系数)
  修复率 = FIXED / (FIXED + PERSISTENT) × 100%
  引入率 = NEW / 总发现数 × 100%
```

#### 落地路径

| 编号 | 任务 | 文件 | 说明 |
|------|------|------|------|
| E1 | 修复状态追踪器 | `fp_sentinel/analysis/fix_effectiveness/tracker.py` | 核心引擎：fingerprint 比对 + 状态分类（FIXED/PERSISTENT/NEW） |
| E2 | 修复质量研判器 | `fp_sentinel/analysis/fix_effectiveness/quality_checker.py` | 分析 commit diff，检测"表面修复"模式（4 种已知误修形态） |
| E3 | 残余风险计算器 | `fp_sentinel/analysis/fix_effectiveness/risk_scorer.py` | 按持续暴露天数加权计算残余风险分 |
| E4 | 修复效果报告 | `fp_sentinel/reporting/fix_effectiveness_report.py` | Markdown 报告输出，含修复率趋势图数据 |
| E5 | CLI 接口 | `fp_sentinel/cli/fix_effect_commands.py` | `fp-sentinel fix-effect show/compare/stats` |

#### API 接口

```
GET  /api/v3/analysis/fix-effect/{project_id}       → 修复效果汇总
GET  /api/v3/analysis/fix-effect/{project_id}/detail → 变更明细（FIXED/PERSISTENT/NEW）
POST /api/v3/analysis/fix-effect/compare             → 两轮扫描 ID 对比
```

#### 关键数据模型

```python
class FixEffectivenessResult(BaseModel):
    scan_id: str
    baseline_scan_id: str
    fixed_count: int
    persistent_count: int
    new_count: int
    fix_rate: float           # 0-100%
    regression_rate: float    # 引入率 0-100%
    residual_risk_score: float # 0-100
    fixed_items: List[FixStatusItem]
    persistent_items: List[FixStatusItem]
    new_items: List[FixStatusItem]
    trend: Optional[List[TrendPoint]]  # 跨多轮趋势

class FixStatusItem(BaseModel):
    finding_id: str
    rule_id: str
    file_path: str
    line: int
    severity: str
    status: Literal["fixed", "persistent", "new"]
    days_persistent: int = 0
    quality_check: Optional[QualityCheckResult] = None
```

- `tests/unit/test_fix_quality_checker.py`：4 种表面修复形态识别 → 8 用例

### 1.2 知识图谱联动

#### 目标

将知识图谱从「被动归档查询」升级为「主动影响分析引擎」。当新发现漏洞时，知识图谱自动给出：
- 历史同类漏洞的修复路径推荐
- 关联组件 CVE 匹配（组件漏洞库已有 15 组件 / 31 CVE）
- 攻击链上下文补全（同一入口的其他历史漏洞串联）

#### 数据流转逻辑

```
[新漏洞 finding]
       │
       ▼
[CWE + rule_id 知识图谱查询]
  ├── kg-match --rule-id <rule_id> → 获取历史同类漏洞修复方案
  ├── kg-search --type <vuln_type> → 获取同项目历史修复记录
  └── 规则 ID → CVE 静态字典 → reference_cve 列表
       │
       ▼
[组件漏洞交叉匹配]
  ├── 扫描项目依赖 pom.xml/go.mod/package.json
  ├── 组件名 → component_vulns.py CVE 库匹配
  └── 版本号范围判定 → 输出受影响的 CVE 列表
       │
       ▼
[攻击链上下文补全]
  ├── 当前 finding 关联的攻击链节点
  ├── 知识图谱中同入口节点的历史链集合
  └── 输出：该节点曾参与的所有攻击路径时间线
```

#### 落地路径

| 编号 | 任务 | 文件 | 说明 |
|------|------|------|------|
| K1 | 知识图谱主动推荐引擎 | `fp_sentinel/knowledge_graph/features/active_recommender.py` | 基于 CWE + 规则 + 组件三维推荐 |
| K2 | 组件漏洞关联器 | `fp_sentinel/vuln_db/component_matcher.py` | 解析依赖文件 → 匹配 component_vulns CVE 库 |
| K3 | 攻击链上下文服务 | `fp_sentinel/attack/v3_ai_pentest/chain_context_service.py` | 接入知识图谱，为 GNN 推理链补全历史上下文 |
| K4 | 推荐结果嵌入器 | `fp_sentinel/reporting/enricher_v33.py` | 将推荐结果嵌入合规报告「⑧ 知识图谱参考增强章节」 |
| K5 | REST API | `fp_sentinel/knowledge_graph/routes_v33.py` | `/api/v3/kg/recommend` / `/api/v3/kg/component-match` |

#### API 接口

```
POST /api/v3/kg/recommend            → 获取漏洞的修复推荐 + CVE + 历史上下文
GET  /api/v3/kg/component-match       → 依赖文件 CVE 匹配
GET  /api/v3/kg/chain-context/{fp}   → 攻击链上下文补全
```

### 1.3 攻击路径推演

#### 目标

基于现有 GNN 攻击链推理引擎（4 头注意力），增强「假设推演」能力：
- 给定一个潜在入口点，推演其最大可能攻击路径（What-If Analysis）
- 给定一个已被修复的节点，计算其对整体攻击面的削减量
- 支持红队视角的攻击场景模拟（仅文本描述 + 已有链模板匹配，零网络）

#### 数据流转逻辑

```
[假设入口点输入]（用户指定 / 自动从 exposure 分析获取）
       │
       ▼
[入口点可达性分析]
  ├── 检索同 CWE 历史漏洞中该入口的利用路径模式
  └── 构建候选节点集 V' = {与该入口 CWE-关联的历史节点}
       │
       ▼
[GNN 约束推理]
  ├── 使用既有 4 头 GAT（因果/风险/距离/拓扑）
  ├── 对候选子图 V' 做多跳路径搜索（max_depth=5）
  └── 每条链输出：到达概率 × 影响面 × 综合风险分
       │
       ▼
[修复影响力量化]
  ├── 选定一条链 C = node_1 → node_2 → node_3
  ├── 计算修复 node_i 后的连通子图变化率
  └──削减量 = (原始链总数 - 修复后链总数) / 原始链总数 × 100%
```

#### 落地路径

| 编号 | 任务 | 文件 | 说明 |
|------|------|------|------|
| A1 | What-If 推演器 | `fp_sentinel/attack/v3_ai_pentest/what_if_reasoner.py` | 基于 GAT 约束推理的入口-路径推演引擎 |
| A2 | 修复影响力评估器 | `fp_sentinel/attack/v3_ai_pentest/repair_impact_analyzer.py` | 节点修复后的攻击面变化量计算 |
| A3 | 推演可视化 | `fp_sentinel/attack/v3_ai_pentest/reasoning_viz.py` | ASCII 路径图 + Mermaid 流程图输出 |
| A4 | CLI 推演命令 | `fp_sentinel/cli/attack_commands.py`（扩展） | `fp-sentinel attack what-if` / `attack impact` |

#### 安全红线（继承 S1/S4）

- What-If 推仪仅基于已有 GNN 推理链做子图检索，不发网络请求
- 攻击场景描述复用 11 种已知链模板 + 通用描述引擎，不生成新 payload
- 所有推演输出标注置信度（HIGH/MEDIUM/LOW）与推理依据

#### 测试覆盖

- `tests/unit/test_what_if_reasoner.py`：入口约束推理 / 连通性变化 → 12 用例
- `tests/unit/test_repair_impact.py`：链削减量计算 / 边界条件 → 8 用例
- **合计目标：≥ 20 用例，覆盖率 ≥ 95%**

## 二、全流程闭环联动

### 2.1 工单对接

#### 目标

将现有 DevSecOps 工单引擎（GitLab/Jira/GitHub 适配器）升级为双向实时联动：
- **扫描→工单**：新漏洞自动创建外部工单 + 关联本地 enterprise_task
- **工单→扫描**：工单状态变更（修复/驳回）自动触发复测扫描
- **工单→通知**：工单超 SLA 自动升级到直属负责人

#### 数据流转逻辑

```
[扫描完成事件]
       │
       ▼
[工单创建决策引擎]
  ├── 按 severity × 策略阈值过滤：
  │    CRITICAL → 立即创建
  │    HIGH → 累计 3 条同类型后批量创建
  │    MEDIUM/LOW → 仅本地记录，不创建外部工单
  ├── 创建请求 → DevOpsAdapter.create_issue() → (ticket_id, key, url)
  └── 写入 finding_ticket_mapping 表 + 创建 enterprise_task 关联
       │
       ▼
[状态双向同步]
  ├── 外部回调（Webhook）→ webhook_handler.py 解析事件
  │    closed/reopened → 更新本地 enterprise_task 状态
  ├── 本地操作（review pass）→ 调用 adapter.close_issue()
  └── 定期同步（每 30 分钟）→ 对比外部工单状态与本地映射
       │
       ▼
[SLA 监控]
  ├── 按 severity 设定 SLA（CRITICAL 24h / HIGH 72h / MEDIUM 7d）
  ├── 轮询任务每 15 分钟检查一次
  └── 超时触发 notify 规则 + 升级到上级角色的 Jira/GitHub mention
```

#### 落地路径

| 编号 | 任务 | 文件 | 说明 |
|------|------|------|------|
| D1 | 工单决策引擎 | `fp_sentinel/devops/ticket_decision_engine.py` | severity 策略过滤 + 批量合并逻辑 |
| D2 | 双向状态同步器 | `fp_sentinel/devops/state_sync_service.py` | Webhook 事件解析 + 定期轮询同步 |
| D3 | SLA 监控器 | `fp_sentinel/devops/sla_monitor.py` | 按 severity 分级的 SLA 计时 + 升级通知 |
| D4 | 统一工单 CLI | 扩展 `fp_sentinel/cli/devops_commands.py` | `fp-sentinel devops ticket sync/stats/sla` |
| D5 | Webhook 事件扩展 | `fp_sentinel/devops/webhook_handler.py` | 增加对 "issue_comment" / "pull_request" 事件的解析 |

### 2.2 整改跟踪

#### 目标

打通 `enterprise_task` 状态机与外部工单 + 自动 PR、复测扫描的全链路跟踪，实现：
- 每个漏洞从发现到关闭的完整时间线
- 整改各阶段耗时统计（识别→分配→修复→验证）
- 整改逾期自动预警

#### 数据流转逻辑

```
[漏洞扫描]
  ↓
[自动创建 enterprise_task]
  状态: pending → assigned（自动匹配模块负责人）
       │
       ▼
[开发者修复]
  ├── 提交 commit → 关联到 task
  ├── 自动 PR 提交（auto_pr.fix + auto_pr.submit）
  │    PR 创建成功 → task.status = fix_submitted
  └── PR 被驳回 → task.status 回退到 in_progress
       │
       ▼
[修复验证]
  ├── 自动触发复测扫描（scheduled 或 webhook event pull_request.merged）
  ├── 复测结果与 baseline fingerprint 比对
  │    完全消失 → task.status = done
  │    仍然存在 → task.status = in_progress（自动添加 review 评论说明残余风险）
  └── 残余风险（fix_effectiveness 判定为部分修复）
       添加 review 评论 → task.status = in_progress
       │
       ▼
[统计分析]
  ├── MTTR（平均修复时间）= AVG(done_at - assigned_at)
  ├── 各阶段耗时 = stage_transition 时间差聚合
  └── 整改完成率 = done_count / total_task_count × 100%
```

|------|------|------|------|
| R1 | 整改时间线追踪器 | `fp_sentinel/enterprise_task/timeline_tracker.py` | 全生命周期时间线聚合（任务+流转+评论+扫描+PR） |
| R2 | 整改进度统计器 | `fp_sentinel/enterprise_task/rectification_stats.py` | MTTR / 各阶段耗时 / 完成率 / 逾期率多维统计 |

### 2.3 自动 PR 提交

在现有 auto_pr 模块（16 类漏洞模板 + 三重校验）基础上，增加：
- PR 提交后的自动复测验证闭环

#### 数据流转逻辑

```
[fp-sentinel auto-pr fix <finding-id>]
       │
       ▼
[auto_fix_generator 生成修复 diff]
  ├── 16 类漏洞模板匹配 → 生成 good_example 替换 bad_pattern

  ├── reference_cve 静态字典 → 关联 CVE
  ├── attack_chain_reasoner 该 finding 的链路上下文 → 嵌入影响说明
  └── fix_effectiveness 上一轮同类修复结果 → 标注修复率预期
       │
       ▼
[PR 提交 → pr_manager]
  ├── GitLab/GitHub adapter.create_pr()
  ├── PR 成功后自动关联 enterprise_task → task.status = fix_submitted
  └── PR 映射写入 repo.pr_mappings 表
       │
```

### 3.1 等保适配

#### 目标

针对等级保护 2.0（GB/T 22239-2019）标准，构建自动化的等保条款映射 + 合规差距评估：
- 每项安全发现自动映射到等保 2.0 适用条款
- 输出等保 2.0 格式的合规差距报告
- 支持按等保「三级/二级」不同等级给出差异化的修复优先级

#### 数据流转逻辑

```
[finding]
       │
       ▼
[等保条款映射层]
  ├── rule_id + cwe_id → 等保条款映射表（静态 YAML 配置）
  │    例：java.sql.injection → 等保 8.1.4.3（安全计算环境-访问控制）
  │         js.xss → 等保 8.1.4.5（安全计算环境-数据完整性）
  ├── 映射结果 = { clause_id, clause_name, grade_requirement }
  └── 未映射的 finding → "其他-待人工判定"
       │
       ▼
[合规差距评估]
  ├── 按 clause_id 聚合未修复 findings
  ├── 合规差距 = 该条款下未修复数 / 该条款下总发现数 × 100%
  └── 差距等级：≥ 50% "严重" / 20%-50% "一般" / < 20% "轻微"
       │
       ▼
[等保报告生成]
  ├── 等保 2.0 格式：条款号 + 条款名称 + 当前状态 + 漏洞清单 + 修复建议
  ├── 三级等保 vs 二级等保差异化输出
  └── 支持导出 Markdown / Word（docx skill）格式
```

### 3.3 批量复测

#### 目标

支持对历史发现（全量/筛选子集）执行一次性的完整复测，验证历史漏洞是否已被修复：
- 按项目 / 规则类型 / 时间范围 / 严重度等维度筛选目标 finding 集
- 增量扫描复测（仅重扫目标 finding 所在文件 + 关联模块）
- 复测结果与原始 finding 逐条比对，生成「已修复/仍存在/部分修复」结论

#### 数据流转逻辑

```
[复测任务创建]
  筛选条件: project_id + 可选(rule_ids / severity / time_range / file_pattern)
  ↓
[目标扫描引擎]
  扫描范围 = 目标 finding 所在文件集 ∪ 关联模块
  扫描器选择: 规则匹配的语言扫描器（复用 ScannerManager）
  ↓
[结果对齐层]
  ├─ 旧 fingerprint 在新扫描中消失 → 已修复
  ├─ 旧 fingerprint 仍存在 → 仍存在
  ├─ 旧 fingerprint 消失但同 CWE 同文件新 finding 出现 → 部分修复/修复引入
  └─ 新发现不在旧集合 → 新增
  ↓
[复测报告]
  ├─ 复测覆盖率 = 已重检数 / 目标总数 × 100%
  ├─ 真实修复率 = 已修复数 / 目标总数 × 100%
  ├─ 逐条对比明细表
  └─ 修复验证失败的 finding "回退"到 enterprise_task.in_progress
```

#### 落地路径

| 编号 | 任务 | 文件 | 说明 |
|------|------|------|------|
| T1 | 复测任务管理器 | `fp_sentinel/retest/retest_manager.py` | 筛选条件解析 + 扫描调度 + 结果对齐 |
| T2 | 复测扫描器 | `fp_sentinel/retest/retest_scanner.py` | 增量扫描 + 4 类结论判定逻辑 |
| T3 | 复测结果对齐器 | `fp_sentinel/retest/result_aligner.py` | 新旧 fingerprint 比对 + 状态判定 + 部分修复检测 |
| T4 | 复测报告生成 | `fp_sentinel/reporting/retest_report.py` | 标准复测报告（覆盖率 + 修复率 + 明细） |
| T5 | CLI 命令 | `fp_sentinel/cli/retest_commands.py` | `fp-sentinel retest task create/run/result/list` |
| T6 | REST API | `fp_sentinel/retest/routes.py` | `/api/v3/retest/tasks` / `/result/{task_id}` |

#### CLI 使用示例

```bash
# 创建复测任务：复测项目 "my-app" 过去 30 天所有未关闭的高危漏洞
fp-sentinel retest task create my-app \
  --severity HIGH,CRITICAL \
  --days 30 \
  --status persistent

# 执行复测
fp-sentinel retest run <task-id>

# 查看复测结果
fp-sentinel retest result <task-id> --format table

# 导出报告
fp-sentinel retest export <task-id> --output ./reports/
```
