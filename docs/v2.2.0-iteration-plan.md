## 二、Agent-Attack 任务书（核二 + 核一增强）

### A1. PoC 模板库 — `fp_sentinel/attack/poc_templates.py`
- 结构：`POC_TEMPLATES: Dict[str, PocTemplate]`，`PocTemplate(vuln_type, cwe, payload_template, description, safety_level, local_verify_fn_name)`
- 覆盖 20 种：sqli-time/sqli-union、xss-reflected/xss-dom、cmd-injection、ssrf、path-traversal、jwt-weak、deser-pickle、deser-yaml、xxe、prototype-pollution、open-redirect、idor、nosql-injection、ssti、weak-hash、hardcoded-secret、debug-mode、csrf-missing、sql-format-string、llm-prompt-injection
- 模板变量：`{target_url}`、`{param}`、`{payload}`；生成时**必须**经过 `_assert_local()`（S1）
- 每个模板配 `safe_explanation`（给报告的防御性说明）与 `reference_cve`（真实 CVE 编号，静态字典）
- 模板内容为**教科书级标准 Payload**（如 `' OR '1'='1`、`<script>alert(1)</script>`、`$(echo fp_sentinel_verify)`），不含任何真实基础设施地址

### A2. 可利用性初筛 + 评分 — `fp_sentinel/attack/exploitability.py`
- `assess(finding, context_lines) -> ExploitabilityResult`
- 初筛规则（Step 1）：是否有用户输入到达危险函数（复用规则 `false_positive_indicators` 反向逻辑 + 窗口 guard 结果）；纯内部常量 → `theoretical`（不可利用）
- 被攻破概率 = 技术风险(CVSS 映射 0-1) × 可达性(公网 1.0 / 内网 0.5 / 本地 0.2) × 资产价值因子(默认 0.8，可配置) ，输出 0-100 百分比
- 技术风险映射：复用/参照 `chain_scorer.ChainRiskScorer` 的分值逻辑

### A3. 攻击链编排 — `fp_sentinel/attack/chain_orchestrator.py`
- 复用 `analysis.chain_discovery.VulnerabilityGraph`：把合规 findings 按文件/入口聚合建图（入口=暴露 HTTP 路由或含用户输入函数；边=同文件调用/同目录组合）
- 单点漏洞 → 直接评分；多漏洞同项目 → 生成路径 `A→B→C`（每步标注漏洞类型/位置/利用难度）
- 输出 `AttackChainReport`（复用 `AttackChain` 模型或新增 pydantic 模型，兼容现有 `models.py` 风格）

### A4. 靶场验证器 — `fp_sentinel/attack/target_validator.py`
- `verify(finding, poc) -> VerifyStatus`，三种状态：`verified_local`（Docker 靶场）/ `simulated`（特征匹配）/ `manual_required`
- Docker 路径：`shutil.which("docker")` 检测；不可用 → 一律 `simulated`
- **模拟验证（默认路径，本环境主用）**：对 `playground/` 靶场或用户项目源码做 payload 特征匹配（PoC 模板中的特征子串是否可达该 sink），零网络
- Docker 路径（可选实现）：`docker run -d --rm -p 127.0.0.1:PORT:PORT` 启动、请求仅发 `127.0.0.1`、finally 中 `docker stop` 自动销毁（S4）
- 全部路径记录验证方式到报告（诚实标注，禁止把 simulated 标成 verified）

### A5. 攻防报告生成器 — `fp_sentinel/reporting/attack_report.py`
- `generate_attack_report(project, findings, chains) -> str`（Markdown）
- 章节固定：① 攻击面总览（ASCII 路径图）② 已验证漏洞表（漏洞/位置/利用难度/验证状态/影响）③ 攻击路径详情（步骤+PoC 代码块+被攻破概率）④ 需人工确认 ⑤ 修复优先级（按概率排序+预计工时）⑥ 安全声明（"PoC 仅用于防御验证" + 生成时间 + 30 天清理提示）
- 报告写入 `--output` 目录（S7 白名单校验）

### A6. 合规报告增强（核一）
- `fp_sentinel/reporting/fix_advisor.py`：`suggest_fix(finding) -> FixSuggestion`（diff 字符串 + 工时估计分钟 + reference_cve + 事故说明）。按规则 ID 建映射表，先覆盖现有 71 条规则中的高频 15 类（SQLi/XSS/命令注入/路径遍历/硬编码密钥/JWT/yaml/pickle/eval/os.system/SSRF/MD5/ECB/debug-mode/open-redirect），其余规则回退通用建议
- `fp_sentinel/reporting/compliance_report.py`：Markdown 合规摘要（趋势表：本次/上次/变化——数据源 `FindingRepo.list_findings` 按时间过滤 + fingerprint 对比新增/修复/遗留；无历史数据时显示首期基线）+ "需关注"列表按 ROI 排序（修复成本 ↑ 严重度 ↑ 顺序）+ Diff 建议块
- 趋势 fingerprint：复用 `FindingRepo.get_by_fingerprint` 既有机制

### A7. CLI 集成 — `fp_sentinel/cli/__init__.py` + `fp_sentinel/cli/attack_commands.py`
- `scan` 命令新增 `--report [compliance|attack|all|none]`（默认 compliance，向后兼容）；输出目录 `--output ./reports/`
- `fp-sentinel attack-purge`：清理 >30 天 PoC/攻防数据（S5）

## 三、Agent-Profile 任务书（核三）

### P1. 数据模型 — `fp_sentinel/profile/models.py`
- pydantic 模型：`DeveloperProfile(alias, display_name, scans_contributed, vuln_counts_by_cwe, avg_fix_hours, fix_pass_rate, repeat_rate, trend, knowledge_gaps)`；`TeamProfile(period, members, health_score, metrics, findings)`
- SQLite 表（沿用 `database/connection.py` 的 Database，**只新增表不改动既有表**）：`developer_alias(id, alias_hash, display_name_encrypted, created_at)`、`profile_snapshot(id, alias_hash, period, metrics_json, created_at)`、`scan_attribution(id, finding_fingerprint, alias_hash, file, committed_at, created_at)`

### P2. 作者归因采集 — `fp_sentinel/profile/attribution.py`
- 只读命令：`git log --format=... --follow -- <file>` 与 `git blame -L <line>,<line> --porcelain <file>`（subprocess 调用，**只读**，加 `--no-pager`）
- 归因策略：finding 行号向 blame 结果最近行匹配 → 作者 email → SHA256 别名化（S6：不存明文 email，display_name 可选存）
- 降级路径：非 git 目录/行号无法归因 → `alias_hash="unknown"`，报告标注"归因覆盖率 x%"
- ⚠️ 每个项目最多缓存 N 条归因记录，避免大仓库性能问题（默认 5000，可配置）

### P3. 画像算法 — `fp_sentinel/profile/analyzer.py`
六维度（对齐框架 5.2）：
1. 漏洞模式偏好：CWE 分布 top3
2. 修复速度：finding 首次发现 → `mark` 为 fixed 的时间差（FindingRepo 状态字段；无数据置空不猜）
3. 修复质量：修复后 30 天内同文件同 CWE 复检复发率
4. 复犯率：同 fingerprint（同规则同文件近邻行）重复出现占比
5. 知识盲区：占比 >30% 的 CWE 类型
6. 成长趋势：按月 finding 数线性斜率
- 团队健康度 0-100：漏洞密度 30 分 + 修复速度 30 分 + 复犯率 25 分 + 高危占比 15 分（各分项相对基准 1.2/千行、72h、20%、10% 打分）
- 验收"与人工判断一致率>80%"的实现方式：用构造数据集写金标准测试（`tests/unit/test_profile_analyzer.py` 内 8+ 断言场景）

### P4. 报告生成 — `fp_sentinel/reporting/profile_report.py`
- `generate_team_report(profiles, period) -> Markdown`：健康度 + 四指标对比行业基准表 + 关键发现（复犯/高危上升归因）+ Top N 个人画像表（**匿名别名**，除非查看者模式为 security_officer）+ 下月目标（由算法自动生成建议值）
- `generate_personal_report(alias)`：本人视角，含团队匿名平均对比
- 报告头部固定隐私声明（S6）；文件写入走 S7 白名单

### P5. 隐私控制 — 融入上述模块
- 别名化默认开启；`--reveal` 仅在 `FP_SENTINEL_REVEAL=1` 环境变量 + `--i-am-security-officer` 双条件下解密显示（本地加密密钥存 SQLite 同目录，README 声明"本地保护非强加密"）
- `profile forget <alias>`：删除 profile_snapshot/scan_attribution 中该别名数据（仅画像库，不碰代码与 findings）
- 代码中不实现任何"评分导出为绩效格式"的接口（注释声明）

### P6. CLI — `fp_sentinel/cli/profile_commands.py`
- `fp-sentinel profile team --month 2026-08 [--project <path>]`
- `fp-sentinel profile me [--alias]`
- `fp-sentinel profile forget <alias>`
- `fp-sentinel profile scan <path>`：扫描并归因入库（内部复用 scanners/manager 或提示先跑 scan 再 `profile build`）
- **不得自行修改 `cli/__init__.py`**（由 Agent-Attack 统一注册）；在模块内暴露 `profile_app = typer.Typer()`

### P 验收标准
1. 构造含 3 个虚拟作者、跨 2 个月的合成 findings 数据 → team 报告健康度/六维度/复犯率计算正确（金标准测试）
2. `git blame` 归因在真实仓库（项目自身）可行；非 git 目录优雅降级
3. 报告中不出现明文 email/姓名（别名化单测：断言输出无原始标识）
4. `profile forget` 后该别名查询为空（单测）
5. `pytest tests/unit/` 全绿，老测试零回归
